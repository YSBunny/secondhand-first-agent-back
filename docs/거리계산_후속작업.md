# 거리 계산 후속 작업

카카오맵 거리 계산 구현을 **크롤러가 실제로 내보내는 주소 데이터**와 대조한 결과다.
상품 140건, 고유 주소 64건 기준이다.

## 필드 표기 규칙

이 문서는 필드를 말할 때 **어느 파트의 어느 필드인지** 항상 함께 적는다.
같은 이름이 파트마다 다른 것을 가리키는 경우가 있어서다.

| 표기 | 뜻 | 정의 위치 |
| --- | --- | --- |
| **크롤러** `location.precision` | 통합 스키마의 필드 | `data-analysis/docs/통합_스키마_정의.md` |
| **백엔드** `Product.latitude` | 이 저장소의 자바 클래스·필드 | `product/domain/Product.java` |
| **AI** `query_parsed.product` | 에이전트 상태·응답 필드 | `ai/docs/노드정의.md` |
| **프론트** `searchResultProduct.distanceKm` | zod 스키마 필드 | `front/src/api/searches/search.schema.ts` |

거리 계산 연동 계약은 **크롤러** 문서 5장 "거리 계산 연동(카카오맵)"에 있다.

---

## 먼저 — 계약은 잘 지켜져 있다

아래는 이미 맞게 구현돼 있어 손댈 필요가 없다.

| 항목 | 백엔드 구현 위치 |
| --- | --- |
| **크롤러** `location.precision`이 `NONE`이면 지오코딩을 건너뜀 | `ProductLocationGeocodeService.geocode` |
| **크롤러** `location.name`이 아니라 `location.full_address`를 씀 | 〃 |
| **크롤러** `location.regions[]` 중 가장 가까운 곳을 고름 | `ProductDistanceRankingService.findNearestLocation` |
| 실패 시 `0`이 아니라 `null`을 씀 | 〃 `putNull("distance_km")` |
| 좌표 없는 상품이 순위를 소비하지 않음 | 〃 `rank` 증가 조건 |
| 카카오 API 키를 코드에 두지 않음 | `application.yaml` → `${KAKAO_REST_API_KEY}` |

특히 마지막 두 개가 중요하다. **거리를 못 구한 상품에 `0`을 넣으면 주소를 읽지 못한
상품이 "가장 가까운 상품"이 되어 추천 1위로 올라간다.** 그걸 피해 두셨다.

아래 작업은 이 위에 얹는 것이다.

---

## 1순위 — 백엔드 `Product`에 좌표 필드가 없다

### 무엇이 문제인가

```java
// 백엔드 product/domain/Product.java
private String location;   // 주소 문자열 하나뿐. latitude / longitude 없음
```

상품을 DB에 저장해도 좌표가 남지 않는다. 백엔드 `/locations/geocode`
(`LocationSearchController.geocodeProductLocation`)는 외부에서 호출하는 엔드포인트일 뿐,
상품 적재 과정에서 불리지 않는다. 캐싱도 없다(`@Cacheable` 없음).

그래서 **검색할 때마다 상품 수만큼 카카오를 호출**해야 한다.

```
검색 1회 = 상품 40건 × 카카오 호출 40회 ≈ 8초
```

시연 중 8초는 치명적이다. 정확도 문제가 아니라 **속도 문제**라 1순위로 둔다.

### 어떻게 고치나

백엔드 `Product`에 좌표를 저장하고, **적재 시점에 한 번만** 지오코딩한다.

```java
// 백엔드 product/domain/Product.java 에 추가
@Column(name = "latitude")
private Double latitude;

@Column(name = "longitude")
private Double longitude;
```

좌표는 상품마다 한 번 구하면 바뀌지 않는다. 같은 동네 매물이 반복돼도 주소가
같으면 결과가 같으므로, **크롤러** `location.full_address`를 키로 하는 캐시를 두면
호출이 더 줄어든다.

> `nullable = true`여야 한다. 지오코딩에 실패하는 주소가 실제로 있다(3순위 참고).
> 실패를 `0.0`으로 채우면 아프리카 앞바다 좌표가 되어 그 상품이 항상 최하위가 된다.

## 2순위 — 백엔드 `Region`에 좌표를 담을 자리가 없다

### 무엇이 문제인가

거리 계산은 **읽을 준비가 돼 있다.**

```java
// 백엔드 product/service/ProductDistanceRankingService.extractCoordinates
addCoordinates(location.path("coordinates"), coordinates);
JsonNode regions = location.path("regions");
if (regions.isArray()) {
    for (JsonNode region : regions) {
        addCoordinates(region.path("coordinates"), coordinates);   // ← 지역별 좌표를 기대
    }
}
```

그런데 **채우는 쪽이 대표 주소 하나만 변환한다.**

```java
// 백엔드 location/service/ProductLocationGeocodeService.geocode
coordinates = kakaoLocalService.findCoordinates(request.fullAddress());
return new ProductLocationGeocodeResponse(..., request.regions(), coordinates);
                                               // ↑ regions를 그대로 반환. 변환하지 않음
```

게다가 백엔드 `ProductLocationGeocodeRequest.Region`에는 **좌표 필드 자체가 없다.**

```java
// 백엔드 location/dto/request/ProductLocationGeocodeRequest.java
public record Region(String name, String fullAddress, String code) { }
//                                                     ↑ coordinates 없음
```

결과적으로 백엔드 `findNearestLocation`은 항상 좌표 1개만 받는다.
**"가장 가까운 곳" 로직이 한 번도 작동하지 않는다.**

### 실제 영향

**크롤러** `location.regions[]`가 2개 이상인 상품이 140건 중 **7건**이다.

| 크롤러 `platform` | 크롤러 `location.regions[].full_address` |
| --- | --- |
| `NAVER_FLEAMARKET` | 부산 수영구 남천동 / 민락동 / **광안동** |
| `NAVER_FLEAMARKET` | 경기 안양시 만안구 석수동 / 안양동 / **박달동** |
| `NAVER_FLEAMARKET` | 부산 금정구 남산동 / 경남 김해시 율하동 / **창원시 상남동** |
| `NAVER_FLEAMARKET` | 부산 수영구 민락동 / 남천동 |
| `NAVER_FLEAMARKET` | 경기 남양주시 화도읍 / 호평동 |
| `JOONGNA` | 경기 군포시 산본1동 / 화성시 진안동 |
| `JOONGNA` | 서울 서초구 양재2동 / 양재1동 |

세 번째 항목이 특히 나쁘다. **부산과 창원은 60km 넘게 떨어져 있다.** 창원 사용자에게
이 상품이 "부산 거리"로 계산되면 사실상 후보에서 밀려난다. 판매자는 창원에서도
거래가 가능하다고 적었는데 그 정보가 버려진다.

### 어떻게 고치나

백엔드 `Region`에 좌표 필드를 추가하고, 지오코딩 시 각 지역을 변환한다.

```java
// 백엔드 location/dto/request/ProductLocationGeocodeRequest.java
public record Region(
        String name,
        @JsonProperty("full_address") String fullAddress,
        String code,
        GeographicCoordinates coordinates   // 추가
) { }
```

**크롤러** `location.regions[]`는 최대 3개라 호출이 3배가 될 수 있지만,
1순위(적재 시 1회 지오코딩 + 캐시)를 먼저 하면 검색 성능에는 영향이 없다.

> 프론트 `searchResultProduct.distanceKm`은 이미 nullable이라 이 작업 전에도
> 화면은 정상 동작한다. 값이 부정확할 뿐이다.

## 3순위 — 행정동 23%가 실패할 수 있다

### 무엇이 문제인가

카카오 `/v2/local/search/address.json`은 **법정동·도로명 기준**이다.
**크롤러** `location.regions[].full_address` 64건 중 **15건(23%)이 숫자가 붙은 행정동**이다.

행정동은 주민센터 관할 구역이라 법정동과 이름이 다르다. 백엔드
`KakaoLocalService.findCoordinates`에는 폴백이 없어서, 실패하면 그대로 좌표가 `null`이 된다.

| --- | --- |
| 경기도 고양시 덕양구 **화정1동** | 화정동 |
| 경기도 군포시 **산본1동** | 산본동 |
| 경기도 수원시 장안구 **조원2동** | 조원동 |
| 경기도 파주시 **금촌2동** | 금촌동 |
| 경기도 화성시 **동탄2동** | 동탄동 |
| 부산광역시 남구 **대연제3동** | 대연동 |
| 부산광역시 동래구 **온천제2동** | 온천동 |

### 어떻게 고치나

백엔드 `KakaoLocalService`에서 원본으로 먼저 조회하고, 실패하면 숫자와 `제`를 떼고
한 번 더 시도한다.

```java
private static final Pattern ADMIN_DONG_SUFFIX = Pattern.compile("제?\\d+동$");

// 1차: 크롤러 location.full_address 그대로
// 2차: ADMIN_DONG_SUFFIX 를 "동" 으로 치환해 재시도
//      "부산광역시 남구 대연제3동" → "부산광역시 남구 대연동"
```

2차도 실패하면 `null`로 둔다. **추측으로 근처 좌표를 넣지 않는다.**

> 법정동으로 바꾸면 정밀도가 살짝 떨어진다(양재1동·양재2동이 같은 좌표가 됨).
> 그래도 동 단위 거리 비교에는 충분하고, 좌표가 아예 없는 것보다 낫다.

## 4순위 — 실제로 몇 건이 실패하는지 재 보기

2·3순위의 심각도는 **실측해야 정확히 알 수 있다.** 카카오 키가 있는 쪽에서
아래 64건을 그대로 던져 보면 30분 안에 답이 나온다.

### 확인할 것

| 질문 | 왜 |
| --- | --- |
| 행정동 15건이 실제로 실패하는가 | 3순위를 할지 말지가 갈린다 |
| 실패 시 숫자를 뗀 주소로 살아나는가 | 폴백 방식이 맞는지 |

## 참고 — 거리가 없으면 총액 계산이 막히는 상품이 있다

**크롤러** `location.precision`이 `NONE`인 상품이 140건 중 **68건(49%)**이다.
이들은 전부 **크롤러** `trade_method`가 `["PARCEL"]`인 택배 전용이라 거리가 필요 없다.
여기까지는 정상이다.

문제는 반대쪽이다. 나머지 72건 중 상당수가 **직거래 전용**(**크롤러** `trade_method`가
`["MEET"]`)이라 **크롤러** `delivery_fee.status`가 `NOT_AVAILABLE`이다. 배송비가 아예
없으므로, 거리를 못 구하면 **총 지불액을 계산할 방법이 없어진다.**

그래서 지오코딩 성공률이 곧 "몇 건을 비교 가능한 상품으로 보여줄 수 있는가"가 된다.
자세한 내용은 `data-analysis/docs/배송비_스코어링_규칙_검토.md`에 있다.

**사용자가 위치를 등록하지 않으면 거리는 전혀 나오지 않는다.**
백엔드 `User.latitude` / `User.longitude`가 `null`이면 AI에 넘기는
`AiUserContext`가 `null`이 되고, 거리 계산 대상에서 빠진다.
온보딩에서 위치 설정을 유도하거나, 미설정 상태를 화면에서 안내해야 한다.
